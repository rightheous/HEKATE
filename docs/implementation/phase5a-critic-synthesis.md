# Phase 5A: Ephemeral Critic and HEKATE Synthesis

Phase 5A adds one durable Critic review to the existing PostgreSQL-backed Task path. The Task remains owned by the persistent HEKATE; the Critic is a bounded, temporary reviewer. The workflow is stored in `critic_workflows`, and worker restart decisions come from its persisted stage and stable operation IDs.

## Workflow and authority

Only a planning operation bound to the persistent HEKATE can accept a `SpawnProposal`. The result handler restores the registry identity from the operation binding and checks the Task, attempt, revision, scope, authorization epoch, completed/quiescent planning execution, current Task state, deadline, cancellation, proposal fields, capability configuration, one-agent/one-review caps, and budget. The proposal cannot select a model, route, grant, registry, or budget.

One transaction accepts the planning result, stores the spawn request hash and workflow, reserves separate Critic and synthesis envelopes in the existing ledger, inserts the ephemeral registry and durable create intent/outbox, increments the Task Critic counter, and moves the Task to `WAITING`. PostgreSQL constraints and Task locking make replay return the same workflow and serialize competing approvals. The Critic profile is snapshotted from server configuration. Critic support is disabled by default in `config/policy.yaml`; enabling it requires a fixed `critic` model profile and the Phase 5A limits set to one.

The create operation ID is also the owner/create tag sent to Letta. If the create response is lost, the workflow remains `CREATE_UNKNOWN`; the worker searches owned agents for the exact owner, tag, and role and links exactly one match. It does not issue another create when the result is absent or ambiguous.

The review capsule carries the original question and constraints, the approved uncertainty target, the uncommitted HEKATE candidate Conclusion, selected bounded Evidence and provenance, any existing Position snapshot, the trusted attempt binding, and deadline/output limits. It uses `reasoning_role=critic` and `targeted_review`. Critic output is the strict `CriticTurnOutput` contract: one bound Conclusion Capsule, with no executable proposal. The result handler checks the immutable Critic binding and actual context manifest before it accepts the Conclusion. Objections are stored as durable dissent IDs derived from the Conclusion and local objection IDs.

After the Critic execution is quiescent and the result is durable, a new attempt and operation run synthesis on the same persistent HEKATE. The stored Critic Conclusion and durable dissent are included in the actual request. The Critic does not authorize or execute its recommendation. Synthesis can return an answer, request more information, abstain, or commit a Position. Position commit still uses the Phase 4 atomic path and HEKATE binding. Only HEKATE's final response is exposed to the user.

Once the Task and Critic execution are terminal/quiescent, a durable delete intent retires the ephemeral Critic. A failed delete remains pending/unknown; after restart the worker rechecks owner/create tags and actual presence before retrying or confirming deletion. Conclusion, dissent, provenance, and ledger rows remain after deletion. Lifecycle create/delete RPCs do not count as provider inference calls.

## Stop and wait convergence verification

The Critic workflow preparation worker now distinguishes a permanent Evidence or authorization denial from a temporary busy/lease wait and an UNKNOWN execution. `EvidenceUnavailable` and `AuthorizationChanged` retain the existing `PolicyDenied` API family while identifying the permanent reason explicitly. BUSY/lease acquisition stays retryable, and an operation or provider call in UNKNOWN remains authoritative: it is not treated as quiescent, its holds are not released, and its Critic is not retired.

When permanent denial is found at `CRITIC_READY` or `SYNTHESIS_PENDING`, a separate PostgreSQL effect transaction re-reads the current Task revision, workflow stage, scope, operation identities, authorization, cancellation/deadline and child execution/call states. For the current revision it records a server-authored `FAILED/POLICY` response, closes that workflow, blocks deferred child steps, releases only proven-unused holds, and inserts the existing durable Critic retirement intent. Actual spend remains settled; unresolved execution and usage are preserved. When the workflow revision is stale, it is closed and safely cleaned up without changing the newer Task. Existing Task cancellation and deadline transitions remain `CANCELLED/USER_CANCELLED` and `FAILED/DEADLINE`.

## Persistent HEKATE create journal reconciliation

The persistent HEKATE bootstrap now binds its provider ID and completes the `agent.create` lifecycle operation in one PostgreSQL transaction. The first transaction claims the deterministic operation/registry identity and durably records `external_call_started` before calling Letta; the runtime call stays outside the transaction. Only that first claimant may call create. Once the start marker exists, retries reconcile by the exact owner, creation tag, and role through the pinned owned-agent list API instead of issuing another create.

The successful create response is checked against owner/tag/role and followed by a targeted `agent.get`. Recovery of an incomplete journal requires exactly one matching runtime agent and checks its ID against any existing registry binding. Provider binding and a `COMPLETED/QUIESCENT` operation observation (provider ID, registry ID, owner, creation tag, role, and confirmation source) commit together. A completed replay checks the stored identity and returns without changing its completion timestamp or observation. A late failed lookup cannot downgrade that completed persistent create; Critic lifecycle state handling remains unchanged. This lifecycle `QUIESCENT` records the end of agent creation only and does not represent inference termination, usage settlement, or a provider cost call.

An absent or ambiguous owned-agent result, lookup failure, owner/tag mismatch, or provider-ID mismatch stays unconfirmed as `UNKNOWN`/`Conflict`; the existing binding is never replaced and an uncertain create is never repeated. This also preserves the unavoidable crash window after the durable start marker but before the runtime call: without a matching owned agent, the row remains unresolved for safe review rather than silently creating another persistent agent.

## Handoff and limits

The Phase 4 Evidence, Position, deadline, authorization, and permit guards remain in place. Critic input is restricted to the Task's selected Evidence and stored manifest. No runtime path enables a Critic tool, recursive spawn, or external mutation.

This phase implements one initial review only. Additional review, continuation, schema repair, transient inference retry, Letta memory projection, Conclusion exact reuse, G7 same-execution resume, and G8 full-request tokenization remain deferred. Production dispatch remains closed; the default Critic setting is disabled and no real provider was called. PostgreSQL is authoritative and any Position memory projection stays durably pending.

For the next step, preserve this phase's operation/attempt identity and accounting boundaries. Any additional review or continuation needs its own explicit cap, budget hold, durable workflow state, and restart/replay probe. Do not treat this implementation or its synthetic pricing as evidence of Critic quality, production routing, or production readiness.
