# HEKATE v0.1 — 통합 검증, 실패 시험, 구현 순서

작성일: 2026-09-29

이 문서의 시험은 **설계된 시험이며 이번 조사에서 실행한 결과가 아니다.** 이번에 수행한 것은 첨부 명세 전체 검토, 현행 Letta 문서 확인, 공개 Git 저장소 세 개의 코드 조사다. 실제 provider 호출·청구·fault injection·성능은 미검증이다.

## 1. 가장 먼저 해결할 통합 의사결정

초기 배포는 전용 self-hosted App Server + local backend로 고정한다. Python Control Plane은 TypeScript bridge를 통해 official SDK로 접속한다. 과거 V1 REST API와 현행 App Server protocol을 한 adapter에 섞지 않는다.

가장 먼저 작성할 코드는 완성된 HEKATE가 아니라 `integration_probe.py`와 작은 bridge다. 다음 gate를 통과해야 실제 사용 가능한 구현으로 진행한다. fake provider를 쓰는 시험을 먼저 수행하고, 비용이 드는 실모델 시험은 설정한 시험 budget 안에서 실행한다.

| Gate | 검증 방법 | 통과 기준 | 실패할 때 |
|---|---|---|---|
| G1 버전·protocol | exact package/runtime/patch pin, hello, capability 조회 | 예상 fingerprint와 일치; 미지원 필드가 조용히 무시되지 않음 | 시작 실패, version lock 수정 후 재시험 |
| G2 agent 생명주기 | 생성→조회→목록→삭제→재조회 | provider ID 연결, 삭제 확인, 다른 소유자 agent 보존 | adapter 보완; 조회 불가 시 UNKNOWN 유지 |
| G3 생성 응답 유실 | 생성 응답을 중간에서 버리고 재시작 | 같은 creation tag로 재발견; 두 번째 객체 생성 없음 | hidden/pagination/consistency 보완; 확정 전 재생성 금지 |
| G4 persistence | HEKATE 대화 후 CP/bridge/server 각각 재시작 | 동일 agent/conversation을 재개, memory/history 유지 | 배포 storage 설정·복구 경로 수정 |
| G5 tool 경계 | Bash, native subagent, web, MCP, scope 탈출 요청 유도 | allowlist 밖 실제 실행 0회, 재연결 후에도 동일 | 해당 backend 사용 중지 또는 enforcement 수정 |
| G6 과금 경계 | model HTTP endpoint를 fake provider로 바꾸고 모든 물리적 호출 기록 | 모든 inference·compaction·retry가 유효한 single-use permit 보유 | runtime guard 보완 전 release 불가 |
| G7 retry/step 제한 | empty output, provider 오류, schema 오류, tool loop 주입 | CP 외 새 inference retry 없음; task cap 초과 0건 | runtime 설정/작은 고정 patch 필요 |
| G8 token/model 설정 | fake provider가 받은 실제 request 검사 | context/output/model 제한이 provider 의미에 맞게 전달 | 지원 모델/배포 제한 또는 adapter 수정 |
| G9 usage | 정상·취소·실패·compaction·cache 경로 비교 | call별 비용 귀속, missing usage는 pending; 중복 청구 합산 없음 | 엄격 모드 비활성/수정, 사용량을 0으로 치환 금지 |
| G10 cancel | 생성·inference·tool 대기·usage 대기 중 취소 | 신규 permit 금지, late result 채택 0, 미정산·cleanup 지속 | provider 한계 표시, 소프트 취소와 실제 중단 분리 |
| G11 serialization | 동일 HEKATE에 두 입력, worker 장애·lease 만료 주입 | 동시 유효 turn 1개, quiescence 확인 전 대체 turn 없음 | lease/recovery 수정 |
| G12 memory projection | 최신 version 투영 후 오래된 job 재전달·전송 실패 | DB current 유지, 오래된 요약으로 최종 판단 안 함 | memory API 보완; 범용 파일 tool로 우회 금지 |

Letta의 고수준 SDK `CreateSessionOptions`에 임의 `max_steps`/`budget` 필드를 넣는 것은 시험이 아니다. 런타임과 provider가 실제 적용한 값을 관찰해야 한다. 조사한 `max_turns` 검사의 존재만으로 G6/G7 통과를 선언하지 않는다.

## 2. capability matrix 저장 형식

`integration/letta/capability-matrix.json`의 각 행은 다음 정보를 갖는다.

```json
{
  "capability": "billable_call_guard",
  "runtime_sha": "exact-sha",
  "sdk_version": "exact-version",
  "backend": "local",
  "model_profile": "fixed-test-model",
  "source_status": "requires_integration",
  "runtime_test_status": "not_run",
  "test_id": "G6",
  "observed_guarantee": null,
  "limitations": [],
  "evidence_artifact": null,
  "tested_at": null
}
```

`source_status`와 `runtime_test_status`는 별도다. 코드에서 메서드를 찾았다는 이유로 tested를 true로 바꾸지 않는다. 모델·SDK·runtime·patch·backend가 바뀌면 영향받는 gate를 다시 검증한다.

## 5. 비교 평가 설계

원 명세의 네 arm을 유지한다.

| Arm | 실행 |
|---|---|
| A | HEKATE 기본 응답 |
| B | 동일 HEKATE의 추가 추론, Critic 없이 실행 |
| C | HEKATE + 필요 시 Critic |
| D | 더 강한 단일 모델 |

동일 비용 조건과 동일 latency 조건은 **별도 실험**으로 수행한다. 두 조건을 동시에 동일하게 만들었다고 주장하지 않는다. fixed evidence snapshot, 같은 문제 순서의 무작위화, arm별 독립 memory, prompt/model/version 기록을 적용한다. C가 Critic을 생성하지 않은 case도 C의 결과로 남긴다.

초기 dataset 제안은 8개 task category별 10개, 총 80개다. 실모델 변동성 확인을 위해 가능하면 case당 3회 반복한다. 80×3은 제안된 pilot 크기이며 통계적 검정력 계산을 대신하지 않는다. 표본이 부족하거나 confidence interval이 넓으면 효용 미확정으로 판정하고 확대한다.

질문에는 정답인 초기 결론, 틀린 사용자 전제, 근거 부족, 중요한 반론, 동일 evidence에서 사용자 주장만 바꾼 짝 문제를 포함한다. grader는 실행 arm을 모르게 하고 사전 rubric을 사용한다. LLM grader만 쓸 경우 중요한 오류·잘못된 판단 변경은 사람이 표본 또는 전수 검토한다.

### 5.1 사전에 고정할 초기 임계치 제안

다음 숫자는 사용자가 이미 정한 요구사항이 아니라 **시작점으로 제안한 기준**이다. 결과를 보기 전에 workload와 운영 예산에 맞게 확정하여 `evals/thresholds.yaml`을 commit한다.

| 항목 | 제안 기준 |
|---|---|
| 권한 밖 tool·scope 접근 | 시험에서 성공 0건 |
| stale/duplicate Position commit | 시험에서 성공 0건 |
| reservation 없는 과금 호출 | 계측한 물리 호출 중 0건 |
| fault suite | F01–F15 기대 상태 모두 충족, unresolved UNKNOWN은 명시된 운영 경로가 있어야 함 |
| 기본 정상 task 완료율 | pilot 95% 이상, 실패/취소/판단 보류를 분리 보고 |
| 단순 질문 unnecessary spawn | 5% 이하 |
| 정답 초기 결론의 잘못된 변경 | 5% 이하, A/B 대비 증가 여부 별도 확인 |
| false objection rate | 사전 판정된 objections 중 10% 이하 |
| evidence traceability | 채택된 근거의 출처 레코드 연결 100%; 원문 재조회 가능성과 별도 |
| Critic 품질 개선 | 대상 category에서 cost-matched B 대비 5점 rubric 평균 +0.3 이상, paired 차이의 95% 구간이 0보다 높음 |
| 실제 비용의 경쟁력 | A/B/D를 함께 비교하여 비용 대비 유효한 이점이 있는 category만 활성화 |
| 단순 경로 latency | 동일 모델 A 대비 C의 비-spawn 경로 p95 증가 10% 이내를 목표로 계측 |
| 추가 review latency | 사전 지정 task deadline 안에 완료. 절대 초 단위 목표는 사용자 workload로 고정 |

운영 안전 지표의 0건은 시험 범위에서의 조건이며 모든 미래 실행에 대한 수학적 증명이 아니다. correctness, unsupported claims, 적절한 abstention, 사용자 주장 변경 민감도는 원 점수와 paired 비교를 모두 보고한다.

미정산 비용은 누락시키지 않고 보수적 hold를 포함한 비용 구간으로 비교한다. runtime compaction, schema repair, retries, final synthesis까지 모두 C의 비용에 들어간다. 실패한 trial을 비용·latency 평균에서 빼지 않는다.

Critic이 B 또는 D보다 낫지 않으면 기본 비활성화하고 검증된 좁은 category만 허용한다. architecture 구현 성공이 multi-agent 효과의 증명은 아니다.

## 6. 구현 순서와 완료 조건

| 단계 | 만들 파일·기능 | 완료 조건 |
|---|---|---|
| P0: 통합 spike | bridge protocol/agents/sessions/limits, version lock, probes, dummy provider | G1–G12 결과 기록, 보완 필요 범위 확정. 특히 G6/G7 실패를 숨기지 않음 |
| P1: domain·store | models/capsules/proposals/transitions/policy, migrations, repositories | ID/schema/상태 규칙, duplicate key/DB atomicity 테스트 통과 |
| P2: 안전한 단일 HEKATE | tasks/turns/budgets, lease, API, worker | 세션 간 지속성, planning/final 비용 계수, cancel·restart 가능한 기본 응답 |
| P3: Critic 한 경로 | lifecycle/scheduler/results/tools/evidence | 1 Critic, 최소 capsule, durable result, 실패 기록 후 cleanup |
| P4: Position·복구 | positions/projections/recovery, inbox/outbox 강화 | atomic commit, stale 차단, F01–F15 통과 |
| P5: bounded deliberation | 추가 review/repair/retry cap, outcomes, response reserve | 무목적 반복 차단, 모든 provider 경로의 budget/권한 gate 검증 |
| P6: 평가·운영 | runner/scoring, dataset/rubric, runbook, metrics | 사전 임계치로 A/B/C/D 비교, Critic 적용 범위 결정 |

원 명세의 Phase 1은 “기본 usage logging”부터 시작하지만, 실제 사용자에게 공개하는 경로에는 최소 budget/cancel/tool 통제를 P2부터 넣는다. 이후에만 안전을 붙이는 구현 순서로 오해하지 않도록 한 보충이다.

첫 PR의 범위는 **domain/schema + version-locked Letta probe**가 적절하다. 다음 PR은 **DB transaction과 bounded single-HEKATE path**다. 처음부터 reasoning role 확장, semantic reuse, sleep, generic workflow engine을 구현하지 않는다.

## 7. design freeze 체크

| 원 명세 freeze 항목 | 이번 산출물 상태 | 최종 동결 전 남은 것 |
